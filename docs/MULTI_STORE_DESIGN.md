# 店舗別 売上一覧 設計書（joe拡張・直営＋FC横断比較）

対象: 柿川亭グループ（直営＝柿川亭・アブララボ ＋ FC＝柿川亭 福島店／白山市場店／新大前店）の日別売上を、既存の経営ダッシュボード「ジョー」（`uriage-dashboard`）に**1画面追加**して横断比較できるようにする。
本書は**設計のみ**。実装はまだ行わない。既存joe・既存シートを一切壊さないことを制約とする。

参照: `docs/APP_DESIGN.md`（画面設計・配色方針）／`docs/DATA_MODEL.md`（直営データモデル）／`index.html`（現行実装）

## 0. 実地検証で分かったこと（最重要・先に読む）

設計に入る前に、対象3シートを実際にgviz（読み取り専用・書き込みなし）で叩いて検証した。**masaのヒアリング内容と食い違う点、想定より危険な落とし穴が見つかった**ため、これを設計の前提とする。

### 0-1. gvizの「タブ名不一致→サイレント フォールバック」問題（★最重要リスク）

gvizの `sheet=<タブ名>` パラメータは、**存在しないタブ名を渡してもエラーにならず、その代わりに黙ってスプレッドシートの先頭タブ（gid=0相当）のデータを返す**ことを実機検証で確認した。

検証例（新大前店シートに対して）：

| リクエストしたタブ名 | 実際に返ってきたタブ（`out:html`の`<title>`で確認） | 一致 |
|---|---|---|
| `デタラメタブ名`（存在しない） | `2026年7月 日別備考` | ✗ |
| `7月の目標設定`（存在しない） | `2026年7月 日別備考` | ✗ |
| `2026年1月〜12月売上`（タスク記載の想定名・実は存在しない） | `2026年7月 日別備考` | ✗ |
| `2026年1月〜2026年12月売上`（探索の末に発見した実名） | `2026年1月〜2026年12月売上` | ✓ |
| `2024年12月〜2025年12月売上` | `2024年12月〜2025年12月売上` | ✓ |

つまり**タブ名を1文字でも間違えたり、masaが将来タブ名をリネームしたりすると、アプリはエラーを出さずに「別の月・別の意味のタブのデータ」を売上として表示し続ける**。これは「誤データを出さない防御」（設計要件2）の核心的な危険源であり、店舗別アダプタは**これを前提に防御を組み込む必要がある**。

**検証で確立した防御手段**：`tqx=out:html` でフェッチすると、返ってきたHTMLの `<title>` タグに**実際にマッチしたタブ名**が入っている（`out:csv`/`out:json`にはこの情報がない）。アダプタは各タブ取得時に

1. `out:html` で `<title>` を取得し、期待したタブ名と**完全一致**するか検証
2. 一致しなければ「このタブのデータは使わない（0扱い・エラー表示）」とし、**フォールバック先の別タブのデータを売上として絶対に採用しない**

という2段構えを必須とする。（`out:csv`単体をいきなり信用しない）

### 0-2. 「年月ヘッダーが年の行＋月の行＋日×金額」という想定は3店舗とも成立しない

タスクの想定（1行目=年、2行目=月、3行目以降=日）を検証したところ、**3店舗すべてで「月」を示すテキスト行は存在しなかった**。実際の構造は：

- **1行目＝年のみ**（例: `2025, 2025, 2025, 2025, …, 2026, 2026…` の数値が列ごとに繰り返される）
- **月を示す文字ラベルはどこにもない**
- 「どの列がどの月か」は**列の並び順（左から時系列順）という慣習でしか分からない**。列ブロックの幅（1列・4列・5列・6列など）も店舗・タブごとにバラバラで、統一ルールが見出せない
- 唯一の例外＝新大前店の「2026年1月〜2026年12月売上」タブだけは **B列=1月、C列=2月…M列=12月の12列固定・隙間なし**というきれいな規則があることを実データで確認（7/31時点でH列＝7月、日30まで入力・日31は空欄で、今日の日付と整合していた）

つまり、**「年月ヘッダーを構造的にパースする」ことは3店舗中2店舗（福島店・白山市場店）では原理的にできない**。列とその月の対応は、**masaに直接確認して固定テーブルとして持つ**しかない（後述の「必要な準備」参照）。

### 0-4. 現状の共有設定について

3店舗とも、**masaによる追加の共有設定変更なしで、gvizが200 OKで実データを返した**（ログイン画面へのリダイレクトやアクセス拒否は発生しなかった）。つまり**現時点で既に「リンクを知っていれば閲覧可能」相当の状態になっている可能性が高い**。ただし、これは「今読めた」という確認であって、masa自身が現在の共有設定を意図的にそうしているかは不明なため、後述の「必要な準備」でmasaに事実確認してもらう（アプリ側が依存する前提として明文化してもらう＝知らないうちに非公開に戻されるとjoeが壊れるため）。

## 1. 全体アーキテクチャ

既存joeは「1個のSHEETSエントリ＝1個のGoogleシートID＝直営2店舗分のタブ」という単純な構造。これに対して今回は**店舗ごとにシートIDもタブ構成も列構造も違う**ため、素直に同じ関数を使い回すことはできない。よって：

```
STORES（店舗レジストリ・配列）
  └─ 各店舗エントリ = { id, name, kind, sheetId, adapter }
        └─ adapter = そのシート固有の「当月の日別売上を吸い出す関数」
              └─ 出力は必ず共通形に正規化: [{date, storeSales, deliverySales, total}, ...]

店舗別売上一覧画面（新タブ）
  └─ STORES を順にループしてadapterを呼び、共通形の配列を受け取る
  └─ 各店舗カードは共通形の配列だけを見て描画する（店舗固有のロジックを画面側に持たない）
```

**設計原則（既存joeのAPP_DESIGN.md「dataviz」方針を踏襲）**:
- 画面コンポーネントは共通形（{date, storeSales, deliverySales, total}）しか知らない。店舗ごとの奇妙な列構造の知識は**アダプタ内に完全に閉じ込める**。
- 店舗追加時にsindex.html本体のロジックを触らずに済むよう、STORES配列に1行足すだけ・対応するadapter関数を1つ足すだけにする（joeの既存 `SHEETS` 配列と同じ思想）。
- アダプタは「分からなければ0件・エラー表示」を徹底し、**フォールバックデータを売上として絶対に混入させない**（0-1節の防御）。

  { id:"abura",     name:"アブララボ",       kind:"直営", sheetId:"1cMfvuwBRc6tnKoeIPAgM5wGryUXyeV5fL2XPkoIcTT8", adapter:"joeTab", tab:"🧴日次：アブララボ" },
  { id:"fukushima", name:"柿川亭 福島店",     kind:"FC",  sheetId:"1jJQLbO2GuMKcL14QEBhb3mjidrNCxyah5Oq9pyp8y_s", adapter:"fukushima" },
  { id:"hakusan",   name:"柿川亭 白山市場店", kind:"FC",  sheetId:"1htLUtSiJQ3qzJIGzAfmFaKuUYskR26vK4GGj_V5_r-A", adapter:"hakusan" },

- 直営2店舗は**既存の`SHEETS`/`TABS`/`parseDaily`をそのまま再利用**する専用アダプタ（`joeTab`）を用意し、既存コードには手を入れない（＝既存joeを壊さない制約を満たす）。

## 3. 店舗別アダプタ設計

### 3-1. 共通出力形

```js
// 1店舗・当月分の配列
[
  { date:"2026-07-01", storeSales:38100, deliverySales:0,     total:38100 },
  { date:"2026-07-02", storeSales:0,     deliverySales:13380, total:13380 },
  ...
]
```

- `storeSales`＝店舗自前の売上（券売機・レジ等、直営でいう券売機売上＋クーポン＋通販等に相当する「配達以外」の合計）
- `deliverySales`＝anydeli／Uber等デリバリー各社の合計
- `total = storeSales + deliverySales`
- 日付が存在しない（未入力）日は配列に含めない、または `total:0` で含めるかは**Phase1で統一ルールをmasaに確認**（質問リスト参照）。既存joeの`parseDaily`は「日付が正規表現に一致する行だけ採用」という防御パターンを踏襲する。

### 3-2. アダプタ共通の処理ステップ（疑似コード）

```js
function fetchTabVerified(sheetId, expectedTabName){
  // ① out:html で <title> を取得し、期待タブ名と完全一致するか検証（0-1節の防御）
  // ② 不一致ならエラーを投げる（フォールバックデータは絶対に使わない）
  // ③ 一致したら out:csv（またはout:json）で本データを取得してパース
}
```

すべての店舗別アダプタは、必ずこの検証つき取得関数を経由してタブを読む。既存joeの直営タブ（`fetchTab`）は現状タブ名が固定・実績があるため当面は据え置きでよいが、将来的に同じ防御を足すことも検討（質問リストではなく将来課題）。

### 3-3. 店舗ごとの差分吸収（列→日付への変換ロジック）

各店舗で「年月ヘッダーの構造」がバラバラであることが実地検証で確定した（0-2節）。アダプタはそれぞれ**個別に「列インデックス→(年,月)」の対応表**を内部に持つ。

| 店舗 | 対応表の形 | 検証で分かった実際の規則性 |
|---|---|---|
| 新大前店 | シンプルな数式：`月 = 列インデックス - 1`（B列=1月〜M列=12月、隙間なし） | 実データで確認済み・信頼度高い。ただし**年が変わったらタブ名ごと変わる**（既存joeのSHEETS配列と同じ運用が必要＝新しい年のタブが出たらレジストリに登録） |
| 白山市場店（シート1／Uber） | 手動マッピングテーブル（列ブロック幅が4列・4列・空白1列・4列など不規則） | 規則性を見出せず。**masaに「この列ブロックは何月か」を直接確認してハードコードするしかない** |
| 福島店（元シート／元データ／デリバリー／日報） | 手動マッピングテーブル（ブロック幅が1・3・4・5・6列と不規則、かつ元データは元シートより内訳列が多い） | 同上。加えて「元シート」（簡易版）と「元データ」（内訳版）のどちらを「その月の正」とするかも要確認（末尾の合計行同士は一致するはずなので、突合検証は可能） |

**「当月」列の自動検出方針（デフォルト案・要masa承認）**：
1. 新大前店のように規則的な店舗は、`今日の月番号`から直接列を計算。
2. 白山市場店・福島店のように不規則な店舗は、手動マッピングテーブルの中から「今日の年・月」に対応するブロックを引く。**マッピングテーブルに該当が無ければ「当月データ未検出」を明示表示し、古い月のデータを当月として誤表示しない**（0-1と同じ防御思想）。
3. さらに保険として、選んだ列ブロックの中に「直近7日以内の日付に対応する非空値が1つもない」場合は画面に⚠️を出す（マッピングがズレている／シート更新が止まっている、のどちらかを早期発見するため）。

### 3-4. 「店舗売上」と「デリバリー売上」の切り分け

- 福島店「元データ」「デリバリー」タブ、白山市場店「Uber」タブのように、**デリバリーが別タブに独立しているケース**は、店舗タブとデリバリータブを日付で突き合わせてマージする。
- 福島店「元データ」のように**1つのタブの中に店舗売上とデリバリー内訳が同居しているケース**は、ブロック内の列位置（合計列／デリバリー内訳の列）をマッピングテーブルで指定する。
- **デリバリー未開始の店舗・月は`deliverySales:0`扱い**にし、「デリバリーは開始したらここに売上金額を入力」のような注記行を売上として誤集計しない（数値でない行はnum()で0になる想定だが、念のため注記セルが日付行に紛れ込むケースを警戒）。

### 4-2. 店舗詳細画面（Phase2）

カードタップで遷移。既存joeのホーム画面にある「日次売上推移」チャートのロジックを再利用し、対象を1店舗に絞って描画：

- 店舗売上／デリバリー売上の内訳（既存の`renderChannel`のパターンを流用、チャネル数が少ないので2区分の横棒でよい）

## 5. masaに依頼が必要な作業（準備リスト）

### 5-1. 共有設定の確認（必須・軽い）
現状、3店舗のシートは追加設定なしでgviz読み取りができている（0-4節）。これが意図した状態か確認し、**「リンクを知っている全員が閲覧可」のまま維持してもらう**ことを明文化してもらう（joeの直営シートと同じ運用に揃える）。編集権限は付与しない。

### 5-2. 会計台帳v2（xlsx）について
`1GGH5b...`＝「会計台帳v2」はExcel形式のためgviz読み取り不可（タスク記載の通り）。**Phase1〜3では対象外**とし、直営データは既存joeが読んでいる公開Googleシート（`1cMfvuwB…`）をそのまま使う。台帳v2を将来使うならGoogleシート化が必要だが、優先度は低いと判断（質問リストで確認）。

### 5-3. タブ名の確定・固定運用のお願い（★最重要）
0-1節の検証で判明した通り、**タブ名が変わると誤データ表示に直結する**。以下をmasaに確認・お願いしたい：

1. 白山市場店の「◯月の目標設定」タブの正式名称（今回のガチ検証では特定できなかった。ただしPhase1では使わないタブなので急ぎ不要）
2. 新大前店の当月売上タブは`2026年1月〜2026年12月売上`で確定か（タスクの記載`2026年1月〜12月売上`とは実際は違う名前だった）
3. 今後**タブ名を変更する際は必ず一声かけてもらう**運用にする（既存joeのDATA_MODEL.mdにある「タブ名を変更しない」ルールと同じ扱いにする）

### 5-4. 列→月のマッピング表の提供（★最重要・実装着手前に必須）
福島店（元シート／元データ／デリバリー）・白山市場店（シート1／Uber）は、月の位置が構造的に読み取れない（0-2節）。実装に入る前に、**masaに「今のシートで何列目から何列目が何月か」を一度だけヒアリングし、固定テーブルとしてコードに埋め込む**必要がある。これは毎月聞くものではなく、シートの構造が変わらない限り一度作れば使い回せる想定（新しい月のブロックが追加されたときだけ更新）。

## 7. masaへの質問リスト

1. **他にFC店舗のシートはあるか**（フォルダ単位で他にもあれば、Phase1のうちに登録しておきたい）
2. 白山市場店の「月の目標設定」系タブの正式名称は？（今回の検証では特定できなかった）
3. 新大前店の当月売上タブは`2026年1月〜2026年12月売上`で間違いないか？（タスク記載の名称とは実際は異なっていた）
4. **福島店「元シート」と「元データ」はどちらを正として扱えばよいか**（元データの方が内訳列が多く新しい形式に見えるが、両者の合計行が一致するか未確認。片方だけ読めばよいのか、月によって使い分けているのか）
5. 各店の「日別売上」として使う正のタブはどれか（目標設定タブ・備考タブ等の非売上タブは除外する前提で、それ以外に紛らわしいタブが無いか）
6. **福島店・白山市場店の「列ブロック→何月か」の対応を教えてほしい**（実装の最初の一歩として必須。新しい月のブロックが追加されたときのルール＝「必ず右側に追加」等の運用習慣も併せて）
7. 当月の判定方法：新大前店のように機械的に決まる店舗はよいが、そうでない店舗で「今アプリが当月だと思っている列」がズレていたときにmasaへ知らせる手段は画面上の⚠️表示で十分か、それとも別途通知が欲しいか
8. デリバリー売上（anydeli/Uber等）は「店舗売上」に含めて一本の売上として見せるか、別建てで比較するか（直営の既存指標＝券売機/anydeli/クーポン/通販の4分類とも整合を取りたい）
9. FCロイヤリティの表示は必要か。必要な場合、税抜金額はシート側の計算行をそのまま信頼してよいか、それともアプリ側で`税抜total×料率`を再計算すべきか（店舗ごとに料率が違う可能性はあるか）
10. データの機密性について：現状FC3店舗のシートは追加設定なしで外部から読み取れる状態だった。これは意図した状態か、それともたまたま共有設定が緩かっただけか（意図的でなければ、joe側の実装前に一度共有設定を見直したい）
11. 未入力日の扱い：当月の日別推移グラフで「まだ入力されていない日」は0として表示するか、グラフから省くか（既存joeの`lineChart`は「データのある最終日までで線を止める」方式を採用している。FC店舗も同じ挙動でよいか）
